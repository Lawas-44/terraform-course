Lección

Detectar errores pronto

Cuanto antes encuentres un error, más fácil es arreglarlo. Terraform y otras herramientas te ayudan en cada momento:

HerramientaQué detecta
terraform validateErrores al escribir el código
validation en variablesValores de entrada incorrectos
precondition y postconditionQue se cumplan condiciones antes y después de crear algo
Bloques checkAvisos sobre el estado de la infraestructura
terraform testQue tu código hace lo que esperas
TFLintValores que no existen y malas prácticas
Trivy y CheckovConfiguraciones inseguras

Tests con terraform test

Terraform tiene su propio sistema de pruebas. Los tests se escriben en archivos que terminan en .tftest.hcl, normalmente en una carpeta tests/. Este es el código que vamos a probar:

Y estos son los tests. Cada bloque run es una prueba:

  • command = plan: solo planifica, no crea nada. Rápido y gratis.
  • command = apply: crea los recursos de verdad y los borra al terminar.
  • assert: lo que debe cumplirse.
  • expect_failures: sirve para comprobar que un valor incorrecto se rechaza.

Trivy y Checkov: seguridad

Estas herramientas revisan tu código y te avisan de problemas de seguridad: buckets públicos, discos sin cifrar, puertos abiertos a todo Internet...

No todos los avisos son errores: una web pública tiene que estar abierta a Internet. Si aceptas un aviso, deja un comentario explicando por qué.

Calidad en Ansible

Ansible también tiene sus herramientas para encontrar errores antes de tocar los servidores:

ComandoQué comprueba
ansible-playbook site.yml --syntax-checkQue el YAML y el playbook están bien escritos
ansible-lintErrores y malas prácticas (módulo 18)
ansible-playbook site.yml --check --diffQué cambiaría en los servidores, sin cambiar nada
Ejecutar el playbook dos vecesQue es idempotente: la segunda vez debe salir changed=0

La prueba de idempotencia es muy importante. Si la segunda ejecución cambia algo, hay una tarea mal escrita (por ejemplo, un command sin changed_when).

ConsejoPuedes probar un playbook en tu propia máquina o en un servidor de pruebas con un inventario distinto: ansible-playbook -i inventario/local.ini site.yml. Para probar roles a fondo existe la herramienta Molecule, que crea contenedores, aplica el rol y lo comprueba.

Práctica guiada

Red de seguridad

  1. Añade una postcondition que verifique que la instancia tiene IP pública.
  2. Escribe dos tests con terraform test (uno que pase, uno con expect_failures).
  3. Ejecuta tflint --init && tflint y corrige los avisos.
  4. Pasa trivy config . y arregla al menos un hallazgo.
  5. Configura pre-commit con los hooks de antonbabenko/pre-commit-terraform.
ImportanteSi has creado recursos en la nube, ejecuta terraform destroy al terminar para no pagar por ellos.

Test

Elige una respuesta en cada pregunta. Verás la explicación al momento. Con un 80 % o más, el módulo está superado.

01¿Qué diferencia hay entre postcondition y un bloque check?

Las condiciones de lifecycle son bloqueantes; los check blocks son informativos.

02En un .tftest.hcl, ¿qué hace command = plan en un run?

Rápido y gratuito, ideal para validar lógica.

03¿Para qué sirve expect_failures = [var.proyecto]?

Así se prueba que las validaciones rechazan valores incorrectos.

04¿Qué permite mock_provider "aws"?

Los recursos se «crean» con valores ficticios.

05terraform validate acepta instance_type = "t3.micra". ¿Qué herramienta lo detecta?

TFLint conoce los valores válidos de cada provider.

06¿Qué herramienta usarías para detectar un bucket S3 público o un disco sin cifrar?

Son escáneres de seguridad de configuración.

07¿Cuál es la forma más segura de gestionar la contraseña maestra de una base de datos RDS?

Así Terraform nunca conoce la contraseña y no termina en el estado.
