Un proyecto = una carpeta

En Terraform, un proyecto es simplemente una carpeta con archivos .tf. Cuando ejecutas un comando, Terraform lee todos los .tf de la carpeta actual (no las subcarpetas) y los trata como una sola configuración. A esa carpeta se le llama root module (módulo raíz).

Para aprender el flujo sin gastar dinero ni configurar cuentas usaremos dos providers que funcionan en tu ordenador:

  • hashicorp/random: genera valores aleatorios (nombres, contraseñas, números).
  • hashicorp/local: crea archivos en tu disco.

Escribe tu primera configuración

Copia esto en main.tf. Debajo lo explicamos bloque a bloque:

  • terraform { ... }: ajustes del propio Terraform. Aquí exigimos versión 1.6 o superior y declaramos qué providers usamos, de dónde salen (source) y qué versiones aceptamos.
  • resource "random_pet" "nombre": un recurso. random_pet es el tipo (lo aporta el provider random) y nombre es el nombre local que tú eliges para referirte a él. Genera algo como gentle-turtle.
  • resource "local_file" "saludo": un archivo en disco. Fíjate en ${random_pet.nombre.id}: estamos usando el resultado de otro recurso. Eso crea una dependencia: Terraform sabe que primero debe generar el nombre.
  • path.module: la ruta de la carpeta actual.
  • output: un valor que Terraform mostrará al terminar.

terraform plan: ver antes de tocar

plan compara tu código con lo que existe y te enseña qué haría. No cambia nada. Es la red de seguridad más importante de Terraform: acostúmbrate a leerlo siempre.

Cómo se lee un plan:

SímboloSignificado
+Se va a crear
-Se va a destruir
~Se va a modificar sin recrear (update in-place)
-/+Se va a destruir y volver a crear (reemplazo)
<=Se va a leer (data source)
(known after apply)El valor aún no se conoce; lo sabremos al crear el recurso

Cambios: actualizar vs reemplazar

Cambia length = 2 por length = 3 y ejecuta terraform plan:

Fíjate en # forces replacement: algunos argumentos no se pueden cambiar sobre la marcha y obligan a recrear el recurso. Con un archivo no importa, pero con un servidor o una base de datos significa perder lo que había dentro. Por eso siempre se lee el plan. Además, como el archivo depende del nombre, también se recrea: los cambios se propagan por las dependencias.

Otro experimento: borra a mano saludo.txt (rm saludo.txt) y ejecuta terraform plan. Terraform detecta que falta y propone crearlo de nuevo. Ha comparado el estado con la realidad.

terraform destroy: limpiar

destroy elimina todo lo que gestiona la configuración. También muestra un plan (con -) y pide confirmación:

El orden ahora es el inverso: primero lo que depende (el archivo), luego aquello de lo que depende (el nombre).

ℹ️ Nota. Resumen del flujo: init (una vez) → plan → apply → … cambios … → plan → apply → destroy al terminar.

🛠 Práctica guiada: Hola, Terraform (carpeta labs/02-primer-proyecto)

  1. Copia el main.tf de ejemplo en una carpeta nueva.
  2. Ejecuta terraform init y explora la carpeta .terraform/.
  3. Ejecuta terraform plan y lee cada línea del plan.
  4. Ejecuta terraform apply y abre saludo.txt.
  5. Cambia length = 3, vuelve a planificar y observa el reemplazo (-/+).
  6. Borra a mano saludo.txt y ejecuta terraform plan: Terraform detecta la diferencia.
  7. Termina con terraform destroy.

⌨️ Comandos clave

ComandoQué haceCopiar
terraform initInicializa el directorio: descarga providers y módulos.
terraform planMuestra qué cambios se harían sin aplicarlos.
terraform applyAplica los cambios (pide confirmación).
terraform destroyDestruye todo lo gestionado por esta configuración.
terraform outputMuestra los outputs.

⚠️ Errores frecuentes

Error: Inconsistent dependency lock file
Has cambiado versiones de providers. Ejecuta terraform init -upgrade.
Ejecutar comandos fuera de la carpeta del proyecto
Terraform trabaja sobre el directorio actual (pwd). Usa cd o -chdir=ruta.

1¿Qué hace terraform init?

init prepara el directorio: backend, providers y módulos. Nunca toca la infraestructura.

2En un plan, ¿qué indica el símbolo -/+?

Es un reemplazo: algún argumento marcado como forces replacement ha cambiado.

3Ejecutas terraform apply dos veces seguidas sin tocar el código. ¿Qué pasa la segunda vez?

Terraform es idempotente: si el estado y la realidad coinciden con el código, no hay nada que hacer.

4¿Cómo sabe Terraform que debe crear random_pet antes que local_file?

Las referencias crean dependencias implícitas; el orden en el archivo no importa.

5¿Qué archivo usa Terraform para recordar qué recursos ha creado?

El estado mapea cada recurso del código con el objeto real que existe.

6¿Qué significa (known after apply)?

Valores como IDs o IPs los genera el proveedor al crear el recurso.
