Capas de protección

Cuanto antes detectes un error, más barato es arreglarlo. Terraform y su ecosistema ofrecen varias capas, de la más temprana a la más tardía:

CapaCuándo actúaDetecta
terraform fmt / validateAl escribirSintaxis, tipos, referencias rotas
Linters (TFLint)Al escribir / en CITipos de instancia inexistentes, malas prácticas
Escáneres (Trivy, Checkov)En CIConfiguraciones inseguras
validation en variablesEn el planValores de entrada incorrectos
precondition / postconditionEn plan y applySuposiciones sobre recursos
Bloques checkAl final del plan/applySalud de la infraestructura (avisos)
terraform testEn CIQue el módulo hace lo que debe

Preconditions y postconditions

Ya conoces validation en variables. Las condiciones van más allá: se ponen dentro del lifecycle de un recurso (o en un output) y pueden usar cualquier valor, incluidos atributos de otros recursos.

  • precondition se evalúa antes de crear/modificar el recurso. Si falla, el plan se detiene.
  • postcondition se evalúa después y puede usar self (el propio recurso).
  • Si una condición falla, Terraform para con un error.

terraform test

Desde la versión 1.6, Terraform tiene un framework de pruebas integrado. Los tests se escriben en HCL en archivos *.tftest.hcl (normalmente en la carpeta tests/). Vamos a probar un pequeño módulo sin nube:

  • Cada run ejecuta un plan o un apply y comprueba sus assert.
  • Los run se ejecutan en orden y comparten estado; al final, Terraform destruye todo lo creado.
  • expect_failures sirve para probar que las validaciones rechazan valores incorrectos.

Mocks: probar módulos de AWS gratis

Con command = apply contra AWS los tests crean recursos reales (lentos y con coste). Desde Terraform 1.7 puedes simular un provider con mock_provider: los recursos «se crean» con valores inventados, sin llamar a la API ni necesitar credenciales.

Linters: TFLint

terraform validate no sabe si t3.micra es un tipo de instancia válido: para él es solo un string. TFLint con el plugin de AWS sí lo sabe, y además avisa de malas prácticas (variables sin tipo, declaraciones sin usar…).

ℹ️ Nota. La versión del plugin aws cambia a menudo; consulta la última en su repositorio de GitHub.

Secretos: cómo gestionarlos

Recapitulando lo que sabemos sobre secretos (contraseñas, tokens, claves):

  1. Nunca en archivos .tf ni en .tfvars subidos a Git.
  2. Pásalos como variables sensitive desde variables de entorno (TF_VAR_db_password) o desde el gestor de secretos del CI.
  3. Mejor aún: que no pasen por Terraform. Deja que AWS los genere y los guarde:
  • Lee secretos existentes con data sources (aws_secretsmanager_secret_version, aws_ssm_parameter), sabiendo que su valor sí acabará en el estado.
  • Las versiones recientes de Terraform (1.10+) añaden valores efímeros (ephemeral) y argumentos write-only (1.11+) que nunca se guardan en el estado. Son la dirección del futuro para secretos.
  • Protege el estado: backend cifrado, acceso restringido por IAM y versionado.

Estimar costes con Infracost

En CI, infracost diff puede comentar en cada Pull Request cuánto cambiará la factura.

🛠 Práctica guiada: Red de seguridad

  1. Añade una postcondition que verifique que la instancia tiene IP pública.
  2. Escribe dos tests con terraform test (uno que pase, uno con expect_failures).
  3. Ejecuta tflint --init && tflint y corrige los avisos.
  4. Pasa trivy config . y arregla al menos un hallazgo.
  5. Configura pre-commit con los hooks de antonbabenko/pre-commit-terraform.
💸 Recuerda: si has creado recursos en la nube, ejecuta terraform destroy al terminar.

⚠️ Errores frecuentes

Tests con command = apply que crean recursos caros
Usa plan o mock_provider siempre que sea posible.
Ignorar avisos de seguridad sin justificar
Si suprimes una regla, deja un comentario explicando por qué.
