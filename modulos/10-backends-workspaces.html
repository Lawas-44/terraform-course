El problema del estado local

Hasta ahora el estado vivía en tu ordenador. Eso tiene problemas serios en cuanto trabajas con más gente (o con un sistema de CI):

  • Compartir: tu compañera no tiene tu terraform.tfstate, así que para su Terraform la infraestructura no existe.
  • Concurrencia: si dos personas hacen apply a la vez sobre el mismo estado, lo corrompen.
  • Pérdida: si se rompe tu disco, pierdes el estado.
  • Seguridad: el estado tiene secretos y está en un portátil sin cifrar.

La solución es un backend remoto: un lugar compartido donde guardar el estado, con bloqueo (locking) para que solo una operación pueda modificarlo a la vez.

BackendDónde guarda el estadoBloqueo
localArchivo en disco (por defecto)Solo en tu máquina
s3Bucket de Amazon S3Archivo .tflock en S3 (use_lockfile)
azurermAzure Blob StorageLease del blob
gcsGoogle Cloud StorageNativo
HCP Terraform (cloud)Servicio de HashiCorpNativo + ejecuciones remotas

  • key es la ruta del archivo dentro del bucket. Usa una por proyecto y entorno: red/prod/terraform.tfstate, web/dev/terraform.tfstate…
  • use_lockfile = true crea un archivo terraform.tfstate.tflock mientras alguien está operando.
ℹ️ Nota. Antes de Terraform 1.10, el bloqueo en S3 requería una tabla de DynamoDB (dynamodb_table = "..."). Lo verás en muchos tutoriales y proyectos existentes; hoy está obsoleto en favor de use_lockfile.
⚠️ Cuidado. Dentro del bloque backend no se pueden usar variables (var.x) ni locals: se evalúa antes que todo lo demás.

ℹ️ Nota. Para entornos tipo dev/prod, la mayoría de equipos prefiere carpetas por entorno que reutilizan módulos (módulos 11 y 14). Los workspaces CLI brillan para copias temporales idénticas.

HCP Terraform

HCP Terraform (antes Terraform Cloud) es el servicio de HashiCorp que, además de guardar el estado, ejecuta los plan y apply en sus servidores, guarda variables y secretos, se integra con GitHub y permite aprobar cambios desde la web. Tiene un plan gratuito limitado.

Alternativas al estilo de HCP Terraform: Spacelift, env0, Scalr o el open source Atlantis.

🛠 Práctica guiada: Estado remoto

  1. Crea (con Terraform, en una carpeta bootstrap/) un bucket con versionado y cifrado.
  2. Añade el bloque backend "s3" a tu proyecto y ejecuta terraform init -migrate-state.
  3. Abre dos terminales y lanza apply a la vez para ver el bloqueo.
  4. Crea los workspaces dev y prod y usa terraform.workspace en un nombre.
💸 Recuerda: si has creado recursos en la nube, ejecuta terraform destroy al terminar.

⌨️ Comandos clave

ComandoQué haceCopiar
terraform init -migrate-stateMueve el estado al nuevo backend.
terraform init -reconfigureReinicializa el backend ignorando la configuración anterior.
terraform init -backend-config=dev.s3.tfbackendConfiguración parcial del backend desde archivo.
terraform force-unlock LOCK_IDLibera un bloqueo atascado (¡asegúrate de que nadie está aplicando!).
terraform workspace listLista workspaces.
terraform workspace new devCrea un workspace.
terraform workspace select prodCambia de workspace.
terraform workspace showMuestra el workspace actual.
terraform loginInicia sesión en HCP Terraform.

⚠️ Errores frecuentes

Error acquiring the state lock
Alguien (o un proceso caído) tiene el bloqueo. Espera o usa force-unlock con cuidado.
Usar variables dentro del bloque backend
No se permite. Usa -backend-config o archivos .tfbackend.
