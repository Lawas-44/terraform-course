Módulo 21

Trabajo en equipo y CI/CD

Flujo con Git y Pull Requests, y GitHub Actions para revisar Terraform y Ansible automáticamente.

Nivel: AvanzadoDuración: 2,5 hTest: 6 preguntasRetos: 2Proyecto: paso 21

Objetivos

Al terminar este módulo sabrás:

  • Organizar un repositorio de infraestructura para varios entornos.
  • Automatizar fmt, validate, plan en cada Pull Request.
  • Autenticar GitHub Actions en AWS sin claves (OIDC).
  • Conocer HCP Terraform y alternativas (Atlantis, Spacelift, env0).

Lección

Organizar el repositorio

Cuando hay varios entornos (desarrollo, producción...), conviene separar los módulos (las piezas reutilizables) de los entornos (donde se usan):

Cada entorno tiene su propio estado. Así, un error en desarrollo nunca afecta a producción.

Trabajar en equipo

En un equipo nadie aplica cambios desde su ordenador. El proceso habitual es:

  1. Creas una rama nueva en Git y haces tu cambio.
  2. Abres un Pull Request en GitHub.
  3. Un sistema automático ejecuta terraform plan y publica el resultado en el Pull Request.
  4. Un compañero revisa el código y el plan.
  5. Al aprobarlo y unirlo a main, el sistema automático ejecuta terraform apply.

Así todo cambio queda revisado y registrado, y nadie necesita las claves de producción en su ordenador.

Guardar el plan y aplicar ese mismo plan

En los sistemas automáticos se guarda el plan en un archivo y luego se aplica exactamente ese plan:

Así se aplica justo lo que se revisó, sin sorpresas.

Otra opción útil es -detailed-exitcode. Hace que plan termine con un número que indica el resultado:

NúmeroSignificado

2Hay cambios pendientes

Conectar GitHub con AWS sin guardar claves

GitHub Actions es el sistema automático de GitHub. Para que pueda crear cosas en AWS no guardes tus claves de AWS en GitHub. Usa OIDC: GitHub pide permiso a AWS en cada ejecución y recibe unas claves temporales que caducan en una hora.

Se configura una vez en AWS:

ImportanteLa línea con sub es muy importante: limita el permiso a tu repositorio. Sin ella, cualquier repositorio de GitHub podría usar tu cuenta de AWS.

El flujo automático en GitHub Actions

Este archivo hace plan en cada Pull Request y apply al unir los cambios a main:

  1. Copia el valor del output role_arn.
  2. En GitHub, ve a Settings → Secrets and variables → Actions y crea el secreto AWS_ROLE_ARN con ese valor.
  3. Abre un Pull Request: verás el plan en la pestaña Actions.

Normas para trabajar en equipo

  • Un solo camino para aplicar cambios: si se hace desde GitHub Actions, nadie lo hace desde su ordenador.
  • Cambios pequeños: son más fáciles de revisar.
  • Lee el plan, no solo el código. Fíjate sobre todo en lo que se va a borrar.
  • Protege la rama main: que no se pueda cambiar sin Pull Request y revisión.

Ansible en GitHub Actions

El mismo flujo sirve para Ansible: en cada Pull Request se revisa el código, y al unirlo a main se puede aplicar.

Para aplicar el playbook desde GitHub Actions hacen falta dos secretos más: la clave SSH privada (para entrar en los servidores) y la contraseña del vault. Se guardan en Settings → Secrets and variables → Actions y se usan así:

Revisiones automáticas en GitHub

Vas a subir el proyecto a GitHub y añadir un workflow que revise Terraform y Ansible en cada cambio. No necesita credenciales de AWS: usa los tests con AWS simulado.

Notaterraform init -backend=false prepara la carpeta sin conectarse al bucket de S3, así el workflow no necesita credenciales.

El último trabajo es especialmente útil: GitHub Actions te presta una máquina Ubuntu, el playbook la configura de verdad y comprueba que la web responde. Así sabes que tus roles funcionan antes de tocar tus servidores.

Abre la pestaña Actions de tu repositorio y comprueba que los dos trabajos terminan en verde.

Resultado de este paso: cada cambio que subas se revisa solo, y verás en GitHub si algo se ha roto.

Práctica guiada

Pipeline de infraestructura

  1. Reorganiza tus labs en modules/ + envs/dev + envs/prod.
  2. Crea el proveedor OIDC y el rol IAM para GitHub (¡con Terraform!).
  3. Añade el workflow de ejemplo y abre un PR para ver el plan.
  4. Añade un job de apply que solo se ejecute al hacer merge en main.
ImportanteSi has creado recursos en la nube, ejecuta terraform destroy al terminar para no pagar por ellos.

Comandos clave

ComandoQué haceCopiar
terraform plan -out=tfplanGuarda el plan en un archivo.
terraform show tfplanMuestra el contenido de un plan guardado.
terraform apply tfplanAplica exactamente el plan guardado.
terraform plan -detailed-exitcodeSale con 0 (sin cambios), 1 (error) o 2 (hay cambios).
terraform -chdir=envs/dev planEjecuta en otra carpeta sin hacer cd.

Elige una respuesta en cada pregunta. Verás la explicación al momento. Con un 80 % o más, el módulo está superado.

01¿Por qué separar envs/dev y envs/prod en carpetas con estados distintos?

Cada entorno tiene su estado y su configuración visibles por separado.

02¿Qué ventaja tiene terraform apply tfplan frente a terraform apply?

Lo que se aprobó en el PR es lo que se ejecuta.

03Con -detailed-exitcode, ¿qué código devuelve plan si hay cambios pendientes?

0 = sin cambios, 1 = error, 2 = cambios.

04¿Qué aporta OIDC frente a guardar access keys de AWS en GitHub?

No hay claves que puedan filtrarse; cada ejecución obtiene credenciales que caducan.

05En la política de confianza del rol OIDC, ¿qué limita la condición sobre sub?

Sin ella, cualquier repositorio de GitHub podría asumir el rol.

06¿Qué permiso necesita el workflow de GitHub Actions para usar OIDC?

Permite solicitar el token OIDC a GitHub.
